# CUC Text-Fabric corpus integrity investigation

**Date:** 2026-09-03 22:17 EEST (UTC+03:00)  
**Reviewer:** GPT-5.6 Sol  
**Repository reviewed:** `DT-UCPH/cuc`  
**Base commit:** `ad69400f5446e1c8217af01659c7c10ab00c015b` (`main`)  
**Primary data version:** `tf/0.2.8`

## Purpose

This note records a focused integrity review of the canonical Text-Fabric data in CUC. The goal is to identify data-model and validation problems that could affect researchers who load the corpus through the Text-Fabric API.

It is intentionally written so that colleagues who do not work with Text-Fabric internals every day can follow the evidence.

## Scope

Reviewed:

- canonical Text-Fabric data under [`tf/0.2.8`](../../tf/0.2.8/);
- `tf/0.2.7` only where useful for version-to-version comparison;
- the root Text-Fabric app in [`app/`](../../app/);
- root corpus tests in [`tests/`](../../tests/);
- the root [`README.md`](../../README.md) where it describes the released corpus.

Explicitly **not reviewed**:

- `agent/`;
- `auto_parsing/`;
- `reviewed/`;
- TSV or CSV files;
- generated/manual morphology work products.

Those files are downstream of the Text-Fabric data or are handled manually in separate branches. Findings below should therefore not be interpreted as a review of the agent or morphology workflow.

## Short summary

The most important issue found is that the Text-Fabric slot type called `sign` contains many whitespace-only nodes, and some `word` nodes contain no readable sign at all. In other words, the TF graph currently mixes actual Ugaritic signs with layout/gap material at the most fundamental slot level.

This matters because researchers normally assume that a `sign` node represents one sign and that a `word` node represents one word. Simple and otherwise reasonable analyses such as counting signs per word can therefore produce misleading results unless the researcher already knows to filter these special nodes.

Other confirmed issues include:

1. empty/whitespace-only `word` nodes in the canonical TF data;
2. a large increase in `sign` nodes from 0.2.7 to 0.2.8 that is disproportionate to the increase in words and deserves converter-level investigation;
3. a mismatch between the `cert` feature values and the root app renderer;
4. default TF text formats that omit the explicit word-divider features;
5. README tablet count `278` while the current TF data contains `279` tablet nodes;
6. root integrity tests that do not test the conditions above;
7. no duplicate tablet labels or trivially duplicated tablet slot ranges found, but duplicate/near-duplicate tablet **content** has not yet been ruled out.

The findings below distinguish confirmed problems from open questions.

---

## 1. `sign` nodes can contain whitespace instead of a sign

**Status:** confirmed  
**Severity:** high for quantitative use

The current type inventory in [`tf/0.2.8/otype.tf`](../../tf/0.2.8/otype.tf) is:

- `1-146017 sign`
- `146018-146351 column`
- `146352-153967 line`
- `153968-154246 tablet`
- `154247-182016 word`

This gives **146,017 sign nodes**, **27,770 word nodes**, and **279 tablet nodes**.

However, [`tf/0.2.8/sign.tf`](../../tf/0.2.8/sign.tf) contains literal spaces and non-breaking spaces as feature values on nodes whose type is `sign`. [`tf/0.2.8/usign.tf`](../../tf/0.2.8/usign.tf) shows the same structural behaviour in the Unicode representation.

A simple example appears at the very beginning of the corpus. The first lexical form is `ḥšk`, but the corresponding word occupies slots `1-5` in [`oslots.tf`](../../tf/0.2.8/oslots.tf). The five `sign` values are effectively:

```text
ḥ
š
k
<space>
<space>
```

So a researcher who asks Text-Fabric for the sign descendants of that word receives five slot nodes even though the lexical form contains three letters.

### Why this is a problem

In Text-Fabric, the slot type is the most basic unit of the corpus graph. It is natural to write code such as:

```python
len(L.d(word, "sign"))
```

and interpret the result as “number of signs in this word”. In CUC 0.2.8 that interpretation is unsafe: the count may include whitespace/layout material.

Likewise, `len(F.otype.s("sign"))` is not safely interpretable as “number of Ugaritic signs in the corpus”.

### Possible intended meaning

The whitespace may be intended to preserve lacuna length, restoration width, or document layout. Preserving that information is useful. The concern is specifically that it is represented as `sign` nodes without a visible sign value, while separate features already exist for interword material.

A clearer model could preserve the information explicitly as a gap/lacuna concept rather than making it indistinguishable from a sign at the node-type level. This review does not prescribe the exact replacement model; it only records the ambiguity in the current interface.

## 2. Some canonical `word` nodes contain no readable sign

**Status:** confirmed  
**Severity:** high

Empty values occur directly in [`tf/0.2.8/g_cons.tf`](../../tf/0.2.8/g_cons.tf). These are not TSV artifacts: they are part of the released Text-Fabric feature data.

More importantly, at least some of those empty `g_cons` values correspond to words whose descendant `sign` nodes are themselves all whitespace.

### Reproducible examples: KTU 1.28 and KTU 1.29

The tablet ranges can be followed through [`tablet.tf`](../../tf/0.2.8/tablet.tf) and [`oslots.tf`](../../tf/0.2.8/oslots.tf).

For **KTU 1.28**, the inspected sequence contains six word nodes with consonantal values equivalent to:

```text
l
<empty>
<empty>
gdlt
<empty>
pl
```

The two adjacent empty words occupy 22 sign slots between them. The corresponding values in [`sign.tf`](../../tf/0.2.8/sign.tf) are whitespace-only. In the inspected region, [`emen.tf`](../../tf/0.2.8/emen.tf) marks those whitespace sign nodes as `restored`.

For **KTU 1.29**, the inspected sequence similarly contains six word nodes of approximately:

```text
<empty>
bl
<empty>
xš
<empty>
xx
```

Again, the empty words are backed by whitespace-only sign descendants.

### Interpretation

These nodes may be intended to encode restored or damaged space. If so, the information is potentially valuable, but the object exposed through Text-Fabric is still typed as a `word` made of `sign` nodes.

That distinction matters for any downstream calculation involving:

- word counts;
- average word length;
- token adjacency;
- n-grams;
- lexical coverage;
- sign frequencies;
- line or tablet density.

A researcher who does not know about this convention can count gap placeholders as words and whitespace nodes as signs.

### Corpus-wide count

The investigation found enough empty values to establish that this is not an isolated one-off, but it did **not** complete a programmatic corpus-wide classification of every empty word/sign combination. A dedicated integrity script should produce the authoritative count before a numerical total is published.

## 3. Large slot-count change between 0.2.7 and 0.2.8

**Status:** confirmed structural change; cause not yet established  
**Severity:** high enough to investigate before the next release

[`tf/0.2.7/otype.tf`](../../tf/0.2.7/otype.tf) contains:

- 117,594 `sign` nodes;
- 27,461 `word` nodes.

[`tf/0.2.8/otype.tf`](../../tf/0.2.8/otype.tf) contains:

- 146,017 `sign` nodes;
- 27,770 `word` nodes.

So 0.2.8 adds:

- **28,423 sign nodes**;
- only **309 word nodes**.

The first word illustrates that the slot representation itself changed: in 0.2.7 it occupies slots `1-4`; in 0.2.8 it occupies slots `1-5`, while its lexical form remains `ḥšk`.

This does not by itself prove that 0.2.8 is wrong. A legitimate change in how gaps or layout are represented could explain it. But because whitespace-only sign nodes are confirmed in 0.2.8, the magnitude and nature of this change should be investigated at the conversion step.

Recommended question for the converter history:

> What intentional source-data or conversion-rule change caused roughly 28k additional sign slots between 0.2.7 and 0.2.8, and how many of those new slots contain readable signs versus layout/gap material?

Until that is answered, comparisons of sign-level statistics across these releases should be treated cautiously.

## 4. The root app tests `cert` against a value that the feature does not use

**Status:** confirmed code/data contract mismatch  
**Severity:** medium/high for display correctness

[`tf/0.2.8/cert.tf`](../../tf/0.2.8/cert.tf) declares `@valueType=str` and contains values such as:

```text
True
False
```

plus empty values.

But [`app/app.py`](../../app/app.py) contains:

```python
if F.cert.v(n) != 'uncertain':
    material = f"""<em>{material}</em>"""
```

No inspected `cert` vocabulary uses the literal value `uncertain`. Therefore this condition does not distinguish the observed `True`/`False` states in the way its name suggests. For `True`, `False`, and empty values, `value != 'uncertain'` is true.

This is a concrete mismatch between feature encoding and renderer logic. The intended visual convention should be checked and the condition aligned with the actual `cert` values.

## 5. Default TF text formats omit explicit word-divider features

**Status:** confirmed interface inconsistency  
**Severity:** medium

[`tf/0.2.8/otext.tf`](../../tf/0.2.8/otext.tf) defines:

```text
@fmt:text-orig-full={sign}
@fmt:text-orig-unicode={usign}
```

At the same time:

- [`trailer.tf`](../../tf/0.2.8/trailer.tf) contains interword material in Latin transcription, including `.`;
- [`utrailer.tf`](../../tf/0.2.8/utrailer.tf) contains Ugaritic word dividers such as `𐎟`.

The custom app manually appends the word trailer while rendering signs. The default Text-Fabric formats do not.

This means that a researcher using the normal Text-Fabric text-format interface can receive a representation that differs from the custom app representation and can lose explicit word-divider information.

The problem is especially confusing in combination with finding #1: whitespace appears in sign slots, while the semantically explicit interword material is stored separately in trailer features that the default format does not include.

## 6. README says 278 tablets; TF contains 279

**Status:** confirmed  
**Severity:** low, but easy to fix

The current [`README.md`](../../README.md) says the corpus contains **278 tablets**.

The current [`tf/0.2.8/otype.tf`](../../tf/0.2.8/otype.tf) defines tablet nodes `153968-154246`, which is **279 tablets**.

The tablet labels in [`tf/0.2.8/tablet.tf`](../../tf/0.2.8/tablet.tf) also enumerate 279 KTU entries. The discrepancy is therefore in the README count, not an unidentified extra node.

## 7. Existing root integrity tests do not detect these failures

**Status:** confirmed  
**Severity:** high as a quality-control gap

[`tests/test_general.py`](../../tests/test_general.py) currently contains a test named `test_tablet_count`:

```python
tablet_count = len(F.otype.s('tablet'))
ind_tablet_count = len(set(F.otype.s('tablet')))
assert tablet_count == ind_tablet_count
```

This checks that Text-Fabric node IDs are unique. It does **not** check:

- that tablet labels are unique;
- that the number of tablets matches documentation;
- that tablets contain text;
- that tablet contents are not duplicated;
- that words contain readable signs;
- that signs contain valid sign values.

The same test file also selects the “latest” TF directory using ordinary lexicographic sorting:

```python
latest_data_folder = sorted(os.listdir(os.path.join(ROOT_DIR, TF_FOLDER)))[-1]
```

This will eventually mis-order semantic versions such as `0.2.10` and `0.2.9`.

### The local transcription comparison is not a release gate

[`tests/hometest_cuc_texts.py`](../../tests/hometest_cuc_texts.py) is explicitly a local-only test and currently contains several issues that prevent it from acting as a reliable corpus-integrity gate:

- a hard-coded Windows repository path;
- a fixture called `verse_transcriptions` while the test requests `line_transcriptions`;
- references to `corpus` nodes/features that do not match the current `otype` inventory;
- spaces and NBSP are removed before comparison, which makes whitespace differences invisible;
- most importantly, `AssertionError` is caught and logged but not re-raised, so a text mismatch does not necessarily fail the test process.

This finding is about the root corpus validation only. It is **not** a review of any tests under `agent/`.

## 8. Duplicate tablets: what was and was not found

**Status:** no trivial duplicates found; content-level audit still open

The current [`tablet.tf`](../../tf/0.2.8/tablet.tf) contains 279 KTU labels, and no duplicate tablet label was found in the inspected inventory.

The tablet-level ranges in [`oslots.tf`](../../tf/0.2.8/oslots.tf) also appear as sequential, non-overlapping slot intervals. No pair of tablet nodes was found that trivially points to the same complete slot range.

This rules out the simplest forms of accidental duplication, but it does **not** rule out duplicated textual content under different labels.

A proper duplicate-content audit should create several fingerprints per tablet, for example:

1. exact ordered sign sequence;
2. exact ordered `g_cons` sequence;
3. normalized sequence with whitespace-only pseudo-signs removed;
4. a structure-aware fingerprint retaining column/line boundaries;
5. near-duplicate similarity for possible duplicated or partially duplicated records.

Near matches would require manual interpretation because ancient texts can legitimately repeat formulae or duplicate compositions.

## Recommended next checks

The following checks would turn this investigation into an enforceable corpus-integrity suite without touching the morphology workflow:

1. **Classify every `sign` node** as readable sign, explicit unknown/damage marker, or whitespace/layout-only value.
2. **List every `word` node with empty `g_cons`** and classify whether it contains any non-whitespace sign descendant.
3. **List every tablet with zero readable words/signs.**
4. **Assert unique tablet labels**, not just unique node IDs.
5. **Fingerprint tablet contents** and report exact and near duplicate candidates.
6. **Verify hierarchy/coverage**: every word belongs to a line/tablet, slots are not accidentally shared across tablets, and section mappings are complete.
7. **Compare 0.2.7 and 0.2.8 programmatically** and explain the 28,423-sign increase by value/category.
8. **Define the allowed vocabulary for `cert`** and test the app renderer against it.
9. **Test the intended text reconstruction** including `trailer`/`utrailer`.
10. **Generate or validate README corpus counts from TF** so documentation cannot silently drift.

These checks should operate directly on `tf/*` and should not use TSV/CSV products as the source of truth.

## Bottom line

The current corpus is loadable as Text-Fabric, but some of the type names exposed to researchers do not have the straightforward meaning they suggest. In particular, `sign` can mean whitespace/gap material and `word` can mean a gap-like object with no readable sign. That is a significant interface and reproducibility risk for quantitative research.

The strongest next step is not to change the data immediately, but to add a small, explicit integrity audit over the canonical TF release. That will establish the exact scale of each category and make it possible to distinguish intended editorial modelling from conversion mistakes before deciding on a migration.
