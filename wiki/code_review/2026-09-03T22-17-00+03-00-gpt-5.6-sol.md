## Purpose

This note records a focused integrity review of the canonical Text-Fabric data in CUC. It asks two separate questions:

1. Is a surprising representation actually wrong?
2. Or is it an established Text-Fabric / ETCBC modelling convention that merely needs to be understood correctly?

To answer the second question, the CUC representation was compared with three related ETCBC corpora:

- [`ETCBC/dss`](https://github.com/ETCBC/dss), TF 2.0;
- [`ETCBC/extrabiblical`](https://github.com/ETCBC/extrabiblical), TF 0.2;
- [`ETCBC/syriac`](https://github.com/ETCBC/syriac), TF 0.9.

This comparison materially changes two of the initial findings. In particular, **non-letter sign slots and empty word-like objects are not automatically data corruption**. The DSS corpus deliberately uses both. The remaining question is whether CUC exposes enough information for a researcher to tell ordinary letters, separators, gaps, and empty placeholders apart.

The note is written for readers who do not need to know Text-Fabric internals in advance.

## Scope

Reviewed:

Those files are downstream of the canonical TF data or are handled separately. Findings below should not be interpreted as a review of the agent or morphology workflow.

## Executive verdict

| Initial observation | Verdict after comparison | Why |
| --- | --- | --- |
| `sign` slots can contain spaces | **Convention in principle; CUC interface problem in practice** | DSS explicitly has `sign` slots of types `cons`, `sep`, `empty`, `missing`, etc. CUC has similar non-letter slots but no equivalent `type` feature and describes `sign` simply as a letter. |
| Some `word` nodes have empty `g_cons` | **Convention in principle; insufficiently typed/documented in CUC** | DSS explicitly supports `word type=empty` and empty slots. Empty CUC words are therefore not inherently malformed. |
| Sign count jumps sharply in 0.2.8 | **Open question, not a proven bug** | It may reflect a deliberate increase in gap/layout fidelity. The release does not explain the change. |
| App checks `cert != 'uncertain'` while data contain `True`/`False` | **Confirmed bug** | Older CUC versions used `uncertain`; current versions changed vocabulary but the renderer did not change with it. |
| Default TF full-text formats omit `trailer`/`utrailer` | **Confirmed interface defect** | DSS, ExtraBiblical, and Syriac include their corresponding after-word material in full text formats. CUC's custom app adds it manually, but standard TF formatting does not. |
| README says 278 tablets but TF has 279 | **Confirmed documentation bug** | Independent of modelling convention. |
| Root integrity tests do not catch the above | **Confirmed QA gap** | Existing tests do not validate the relevant code/data contracts. |
| Empty `@source`/`@manuscripts` | **Documentation/provenance gap, not a format violation** | Comparable corpora vary in where provenance is recorded. |
| Duplicate tablets | **No trivial duplicates found; content-level check still open** | Labels and tablet slot ranges look unique; normalized content fingerprints have not yet been exhaustively compared. |

The most important correction to the initial review is therefore:

> **The problem is not that CUC contains non-letter slots or empty words. Those are defensible corpus-modelling conventions. The problem is that CUC does not expose the distinction clearly enough for researchers to use those conventions safely.**

## 1. What DSS establishes as a legitimate convention

DSS is the closest comparator because, like CUC, it uses individual signs as Text-Fabric slots.

In DSS 2.0, `otype.tf` defines more than 1.4 million `sign` slots. Its feature documentation explicitly says that a sign is the basic unit and can be more than a consonantal letter. The DSS `type` feature distinguishes, among other categories:

- `cons` — consonantal letter;
- `vwl` — vowel;
- `sep` — separator, including a space;
- `punct` — punctuation;
- `missing` — missing sign;
- `unc` — uncertain sign;
- `term` — end-of-line marker;
- `empty` — an empty placeholder.

DSS also explicitly permits empty words. Its documentation states that a word may contain “a string of consonants, a numeral, punctuation, nothing, ...”. When source transcription is empty but a word object is still required, DSS can create the word and attach an `empty` sign slot.

This is decisive for the review: **neither a whitespace-valued sign slot nor an empty word is automatically a corpus error.**

DSS also demonstrates how that model is made safe for users. Its tests reconstruct consonantal material by selecting only descendant signs whose `type` is `cons`, instead of assuming that every descendant `sign` is a consonant.

Conceptually, DSS does this:

```python
letters = "".join(
    F.glyphe.v(s)
    for s in L.d(word, "sign")
    if F.type.v(s) == "cons"
)
```

That explicit classification is the important part of the convention.

### Consequence for the original CUC finding

The earlier wording “whitespace pseudo-signs are corruption” was too strong and is withdrawn.

The correct question is:

> Can a CUC user distinguish a real Ugaritic letter from a separator, missing/restored position, vacant space, or other non-letter slot without reverse-engineering several other features?

At present, the answer appears to be **no**.

## 2. CUC lacks the DSS-style classification that makes non-letter slots safe

**Status:** confirmed modelling/interface issue  
**Severity:** medium/high for sign-level quantitative research

CUC 0.2.8 describes the `sign` feature as:

```text
@description=consonantal letter in latin script
```

The README similarly says:

```text
sign: Letter in Latin script
```

But `sign.tf` contains ordinary spaces and non-breaking spaces as values on slot nodes of type `sign`.

Unlike DSS, CUC 0.2.8 does not provide a `type` feature that says whether a slot is a consonant, separator, empty/gap position, missing sign, punctuation, or another category.

This means that code which looks entirely reasonable from the CUC documentation can silently count non-letter material:

```python
len(L.d(word, "sign"))
```

That number is a count of **slots**, not necessarily a count of Ugaritic letters.

### A concrete ordinary-word example

This ambiguity is not limited to heavily damaged texts.

At the beginning of the corpus, one word has:

```text
g_cons = ʿmy
```

Its slot span is five sign slots, whose `sign` values are:

```text
ʿ
m
y
<space>
<space>
```

The two trailing spaces are not marked as emendations in the aligned `emen` values. The same word also has an explicit `trailer` value `.`.

So this is not simply “a damaged word represented by missing positions”. At least some ordinary word-boundary/layout spaces occur inside the sign span while a separate feature simultaneously represents interword material.

That is a real usability problem even though non-letter sign slots themselves are a valid convention.

### Recommended resolution

The safest model would be to add an explicit categorical feature analogous to DSS, for example a sign-slot classification such as:

```text
cons
sep
missing
restored-gap
empty
other
```

The exact vocabulary should follow CUC's editorial model rather than copy DSS mechanically. The important property is that a researcher can reliably select actual written/reconstructed letters without inspecting Unicode whitespace or inferring intent from unrelated features.

If adding a feature is not desirable, the minimum alternative is precise documentation plus a supported helper/query showing how to distinguish the categories. A first-class feature is preferable because it is testable and queryable.

## 3. Empty CUC words are not inherently wrong, but they need an explicit semantic category

**Status:** convention confirmed; CUC representation remains ambiguous  
**Severity:** medium

CUC contains word nodes with empty `g_cons`. Some consist entirely of whitespace-valued sign slots. KTU 1.28 and 1.29 provide clear examples.

For KTU 1.28, an inspected six-word sequence is approximately:

```text
l
<empty>
<empty>
gdlt
<empty>
pl
```

For KTU 1.29:

```text
<empty>
bl
<empty>
xš
<empty>
xx
```

Several of those whitespace-only slots are marked `emen=restored`, strongly suggesting editorially meaningful absent/restored positions rather than accidental empty strings.

The DSS comparison changes the interpretation. DSS explicitly models `word type=empty`, so preserving a gap-like textual object as a word is an established approach. ExtraBiblical also uses `word` as its slot type and contains absent/empty surface-feature values, reinforcing that an empty textual realization does not by itself imply corruption.

### What remains problematic in CUC

CUC does not give these words a machine-readable word type such as `empty`, `gap`, or `lacuna`.

As a result, a downstream user who simply writes:

```python
len(F.otype.s("word"))
```

cannot tell from `otype` whether all counted objects are lexical words or whether some are editorial placeholders/gap objects.

This affects interpretation of:

- token counts;
- average word length;
- n-grams and adjacency;
- lexical coverage;
- density by line/tablet.

The recommended fix is therefore **classification and documentation**, not deletion of empty words.

## 4. The 0.2.7 → 0.2.8 sign-count increase is not proven to be a regression

**Status:** unexplained model change  
**Severity:** investigation/documentation item, not currently a defect

The released node inventories changed from:

### 0.2.7

- 117,594 `sign` nodes;
- 27,461 `word` nodes.

### 0.2.8

- 146,017 `sign` nodes;
- 27,770 `word` nodes.

Difference:

- **+28,423 sign slots**;
- **+309 word nodes**.

The slot layout of existing words also changed. For example, the first `ḥšk` word occupies four slots in 0.2.7 and five in 0.2.8.

An initial review treated the very large increase in whitespace-valued slots as evidence of a likely regression. After comparison with DSS, that conclusion is no longer justified: a sign-slot corpus may intentionally add space/gap/empty positions to preserve more source information.

However, the change is large enough that it should be explained. The commit introducing TF 0.2.8 is simply titled `TF 0.2.8`; the reason for the changed slot policy is not evident from the release itself.

Recommended action:

- document what changed in the conversion/model between 0.2.7 and 0.2.8;
- classify the newly represented slot material;
- state whether sign-level statistics are expected to be comparable across those releases.

Until then, treat cross-version sign counts cautiously, but **do not call the increase a data bug without converter/source evidence**.

## 5. Confirmed bug: the app renderer still expects the old `cert` vocabulary

**Status:** confirmed code/data contract regression  
**Severity:** high for display correctness

Current CUC 0.2.8 `cert.tf` stores string values such as:

```text
True
False
```

plus absent values.

The root app still contains:

```python
if F.cert.v(n) != 'uncertain':
    material = f"""<em>{material}</em>"""
```

This condition cannot distinguish the current `True` and `False` states: both are different from the literal string `uncertain`.

The repository history makes the cause especially clear. CUC 0.2.5 still used the literal value:

```text
uncertain
```

whereas the file under `tf/0.2.6/cert.tf` already contains `True`/`False` values (its internal metadata says version 0.2.7). The app logic was evidently written for the older vocabulary and was not migrated with the data.

This is not a corpus convention. It is a straightforward stale renderer/data-contract bug.

The intended polarity of the current boolean-like strings should be confirmed from the converter, then the app condition and tests should use the current representation consistently.

## 6. Confirmed interface defect: CUC “full text” formats omit the explicit trailer

**Status:** confirmed by cross-corpus comparison  
**Severity:** medium/high

CUC 0.2.8 defines:

```text
@fmt:text-orig-full={sign}
@fmt:text-orig-unicode={usign}
```

But CUC also has:

- `trailer` — documented as interword material in Latin script;
- `utrailer` — the Unicode counterpart, including Ugaritic word dividers;
- a custom app that manually appends the parent word's trailer while rendering signs.

So the custom app knows that trailer material is part of the displayed text, but the standard Text-Fabric “full” formats do not include it.

### The three comparison corpora point in the other direction

**DSS 2.0** includes `{after}` in its full text formats, e.g.:

```text
@fmt:text-orig-full={glyph}{punc}{after}
```

Its `after` feature is explicitly “space behind the word, if any”.

**Syriac 0.9** defines:

```text
@fmt:text-orig-full={g_cons_utf8}{trailer}
```

and its README explicitly documents `trailer` as material that comes after a word.

**ExtraBiblical 0.2** defines full formats with `{g_suffix}` / `{g_suffix_utf8}`, and those features contain spacing material.

CUC is therefore the outlier: its explicit after-word/divider feature is omitted from its default full-text format.

### Why it matters

A researcher using standard Text-Fabric text reconstruction may receive a different representation from the CUC app and may lose explicit Ugaritic word-divider information without realizing it.

The likely fix is to define a supported word-level or sign-level full format that includes the relevant `trailer`/`utrailer` material exactly once.

Care is needed because some spacing is currently also present inside sign spans. The format should be tested against intended source reconstruction rather than simply concatenating every available whitespace field.

## 7. README tablet count is wrong

**Status:** confirmed documentation bug  
**Severity:** low

The current README says:

```text
278 tablets
```

CUC 0.2.8 defines tablet nodes `153968-154246`, which is **279 tablet nodes**. The listed KTU ranges also expand to 279 entries.

This is not a modelling convention. The documented count should be corrected or generated/validated automatically from the released TF data.

## 8. Root validation is too weak to protect the public TF interface

**Status:** confirmed QA gap  
**Severity:** medium/high

The root test named `test_tablet_count` currently compares the number of tablet node IDs with the size of a Python `set` made from the same node IDs. Since Text-Fabric node IDs are already unique identifiers, this does not validate the expected tablet count or tablet labels.

There are no root release tests that currently establish the most important contracts discussed above, for example:

- allowed `cert` values and renderer behaviour;
- which sign-slot categories exist;
- how to reconstruct `g_cons` from sign descendants;
- how gap/empty words are identified;
- whether the standard full-text format preserves intended word dividers;
- expected tablet count and unique tablet labels.

DSS provides a useful model here: one of its tests reconstructs consonantal content only from sign slots whose `type` is `cons`, and compares that result with word-level `g_cons`. CUC cannot currently write an equivalent robust test because it lacks the corresponding sign classification.

### `hometest_cuc_texts.py`

The local transcription comparison is not an effective release gate in its current state. Among other issues, it:

- contains a hard-coded Windows path;
- is not named like a normal pytest-collected `test_*.py` module;
- uses fixture/node assumptions that do not match the current corpus;
- removes ordinary spaces and NBSP before comparison, hiding distinctions that matter to the sign-slot model;
- catches `AssertionError` without re-raising it, so a mismatch need not fail the test run.

This observation is strictly about root corpus validation, not `agent/` tests.

### Version-directory sorting

CUC, DSS, and Syriac all contain code that selects the latest TF folder using lexicographic sorting:

```python
latest_data_folder = sorted(os.listdir(...))[-1]
```

So this is a shared ETCBC-family pattern rather than a CUC-specific anomaly. It is still a latent bug: `0.2.9` sorts after `0.2.10`. It does not currently explain any CUC data problem, so it should be treated as maintenance debt rather than a present corpus defect.

## 9. Provenance metadata is incomplete, but this is not a TF-convention violation

**Status:** documentation/reproducibility gap  
**Severity:** low/medium

CUC feature headers currently have empty fields such as:

```text
@source=
@manuscripts=
```

The comparison corpora are not completely uniform:

- DSS places a concrete source description directly in TF metadata;
- Syriac gives a generic source in TF metadata and detailed edition-level provenance in its README;
- ExtraBiblical records its source/version history primarily in repository documentation.

Therefore an empty `@source` field is not, by itself, proof that the CUC data violate a Text-Fabric convention.

The practical issue is reproducibility: the CUC README identifies KTU generally, but the released TF data should make it easier to determine exactly which edition/source/version and conversion procedure a given release represents.

This is best classified as a provenance improvement, not a corrupt-data finding.

## 10. Duplicate tablets: no simple duplication found, deeper fingerprinting still open

**Status:** no trivial duplicates found; content-level audit remains open

The current tablet inventory contains 279 KTU labels, with no duplicate label found in the inspected inventory.

Tablet-level `oslots` ranges are sequential and non-overlapping; no two tablet nodes were found pointing to the same complete slot span.

That rules out simple structural duplication. It does **not** yet rule out two differently labelled tablets carrying identical or near-identical normalized content.

A separate content audit should compute at least:

1. exact ordered sign-slot fingerprints;
2. ordered `g_cons` fingerprints;
3. fingerprints after classifying/removing non-consonantal layout slots;
4. line/column-aware fingerprints;
5. near-duplicate candidates for manual review.

Near duplication is not automatically an error because ancient corpora contain genuinely repeated formulae and parallel texts.

## Recommended release-level contracts

Rather than forbidding editorially useful empty/gap material, CUC should make its intended model explicit and test it.

A useful release integrity suite would establish:

1. **Sign-slot classification:** every slot can be identified as a consonant, separator, missing/restored position, empty/gap position, or another documented category.
2. **Word classification:** lexical words and editorial empty/gap placeholders are distinguishable in the API.
3. **Consonantal reconstruction:** filtering sign descendants to consonantal signs reconstructs the intended word-level `g_cons`, with documented exceptions.
4. **Text reconstruction:** the supported full-text format preserves intended word dividers and spacing exactly once.
5. **Renderer contract:** the app interprets every allowed `cert` value correctly.
6. **Section integrity:** tablet labels are unique, the released tablet count is expected, and section/slot mappings are complete.
7. **Cross-version model notes:** releases that materially change slot semantics say so explicitly.
8. **Provenance:** a user can identify the source edition/data version and conversion version for a released TF dataset.

These tests should operate directly on canonical `tf/*`. TSV/CSV products should not be used as the source of truth for this audit.

## Bottom line

The cross-corpus check removes the strongest accusation from the initial review: **CUC is not wrong merely because some `sign` slots are spaces or some `word` nodes have no consonantal text. DSS demonstrates that both can be intentional Text-Fabric corpus conventions.**

What remains is more specific and better supported:

1. **CUC does not expose the semantic category of its non-letter sign slots the way DSS does.** This makes sign-level quantitative use unnecessarily error-prone and conflicts with CUC's own description of `sign` as a letter.
2. **Empty/gap words are plausible editorial objects, but CUC does not type them explicitly**, so generic word counts are semantically ambiguous.
3. **The app's `cert` renderer is genuinely stale:** the data moved from `uncertain` to `True`/`False`, while the app still tests for `uncertain`.
4. **CUC's standard “full text” format genuinely omits explicit trailer/divider material**, unlike DSS, ExtraBiblical, and Syriac.
5. **The README count of 278 tablets is genuinely inconsistent with the 279 released tablet nodes.**
6. **The large 0.2.8 slot increase is an unexplained model change, not a demonstrated regression.**

That distinction should guide any fixes: preserve editorial information, but make the categories explicit, documented, reconstructable, and testable.
