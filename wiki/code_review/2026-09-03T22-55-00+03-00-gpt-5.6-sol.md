# CUC Text-Fabric slot-model verification

**Reviewer:** GPT-5.6 Sol  
**Repository:** `DT-UCPH/cuc`  
**Canonical corpus reviewed:** `tf/0.2.8`  
**Reference base commit:** `ad69400f5446e1c8217af01659c7c10ab00c015b` (`DT-UCPH/cuc:main`)  
**Review branch:** `code-review/tf-integrity-20260903-2217-gpt-5-6-sol`

This is a follow-up to the earlier integrity review in [`2026-09-03T22-17-00+03-00-gpt-5.6-sol.md`](./2026-09-03T22-17-00+03-00-gpt-5.6-sol.md). It specifically checks whether the surprising CUC representations identified there are actual defects or established corpus-modelling conventions.

The main conclusion is important:

> **The whitespace slots and empty `g_cons` words are not evidence of lost or corrupted Ugaritic text. They are defensible ways of representing separators, gaps and editorial material. The real problem is that CUC does not type or document those objects clearly enough for researchers to distinguish them safely.**

At the same time, the audit confirms a few genuine bugs and reveals a very specific representation change between TF 0.2.7 and 0.2.8.

## Executive verdict

| Observation | Verdict after verification |
| --- | --- |
| Whitespace occurs in `sign` slots | **Not corruption.** Comparable DSS modelling permits non-letter sign slots. **CUC still has an interface/schema problem** because it calls `sign` a letter and provides no `type` feature. |
| Some `word` nodes have empty `g_cons` | **Not lexical data loss.** All 528 such nodes are gap/punctuation/editorial objects. **They should be explicitly typed.** |
| 0.2.8 has many more sign slots than 0.2.7 | **Confirmed representation change, not proven corruption.** Almost all of the growth is ordinary trailing ASCII whitespace attached to words. This should be documented and tested because sign-level statistics change dramatically. |

| README says 278 tablets | **Confirmed documentation bug.** TF 0.2.8 contains 279 tablet nodes. |
| Some tablets might contain only symbols/gaps | **Not found.** Every tablet has visible signs and at least one non-empty `g_cons` word. |
| Duplicate tablets | **No exact duplicates found** under either visible-sign or non-empty-word fingerprints. Near-duplicate literary content was not assessed here. |

# 1. What the slot layer actually contains

[`tf/0.2.8/otype.tf`](../../tf/0.2.8/otype.tf) defines **146,017 `sign` slots**.

The complete audit divides them into three useful semantic groups:

| Class | Slots | Percent of all slots |
| --- | ---: | ---: |
| Consonantal sign values used by `g_cons` | **77,215** | **52.88%** |
| Whitespace (`U+0020` or NBSP) | **68,256** | **46.75%** |
| Visible non-consonantal/editorial signs | **546** | **0.37%** |
| **Total** | **146,017** | **100%** |

The 546 visible non-consonantal signs are completely accounted for by:

| `sign` value | Count | Meaning visible from the parallel Unicode layer |
| --- | ---: | --- |
| `.` | **517** | maps to Ugaritic word divider `𐎟` |
| `?` | **16** | editorial/uncertainty marker |
| `-` | **10** | non-consonantal editorial material |
| `…` | **3** | ellipsis/editorial material |

The important correction to the first review is therefore that the CUC slot layer is not really a layer of letters. It is a **mixed atomic transcription layer** containing letters, whitespace, dividers and editorial signs.

That is a legitimate design in Text-Fabric. The problem is the public contract. [`sign.tf`](../../tf/0.2.8/sign.tf) describes the feature as `consonantal letter in latin script`, [`usign.tf`](../../tf/0.2.8/usign.tf) similarly describes a consonantal letter in Ugaritic script, and the README says `sign: Letter in Latin script`.

A researcher cannot infer from those descriptions that nearly half of all `sign` slots are whitespace and another 546 slots are punctuation/editorial signs.

# 2. DSS shows that non-letter sign slots are an established convention

This is where the comparison with [`ETCBC/dss`](https://github.com/ETCBC/dss) materially changes the diagnosis.

DSS also uses `sign` as its Text-Fabric slot type. Its feature documentation explicitly says that a sign may be:

- `cons` — consonant;
- `vwl` — vowel;
- `sep` — separator, including a space;
- `punct` — punctuation;
- `missing` — missing sign;
- `unc` — uncertain sign;
- `term` — line terminator;
- `empty` — an empty placeholder.

In other words, **DSS does not assume that every `sign` slot is a written letter**.

The crucial difference is that DSS exposes the distinction through a `type` feature. Its own integrity test reconstructs `g_cons` from word descendants by taking only signs for which `type == 'cons'`.

That makes code such as “count consonants” unambiguous.

CUC has no equivalent `type.tf`. The same distinction can be reconstructed indirectly from feature values, but researchers should not have to reverse-engineer it.

### Recommended model

CUC does not need to remove whitespace or editorial slots. A safer change would be to type them explicitly, for example with categories along the lines of:

- `cons`;
- `sep`;
- `punct` / `divider`;
- `editorial`;
- `gap` / `empty`.

The exact vocabulary should reflect CUC editorial semantics rather than copy DSS mechanically. The important point is to expose the distinction as data.

# 3. The 528 empty `g_cons` words do not contain lost lexical text

TF 0.2.8 has **27,770 word nodes**. Of these:

- **27,242** have non-empty `g_cons`;
- **528** have empty `g_cons`.

The earlier review treated the empty words as potentially malformed. The full audit shows that this was too strong.

All 528 empty `g_cons` words fall into explicit non-lexical categories:

| Empty-word class | Count |
| --- | ---: |
| Whitespace/gap placeholder only | **519** |
| Divider-only (`.` → `𐎟`) | **3** |
| Other editorial-only (`…` or `-`) | **6** |
| Empty `g_cons` with unexplained consonantal letters | **0** |

Examples include:

- KTU 1.1 line 5: an 18-slot whitespace-only word, all 18 slots marked `emen=restored`;
- KTU 1.25 line 10: an empty `g_cons` word whose only visible sign is `.` / `𐎟`;
- KTU 1.6 lines 29 and 30: empty `g_cons` words consisting of `…`;
- KTU 2.103: several empty `g_cons` objects consisting of `-` signs.

This closely resembles the DSS convention. DSS explicitly supports word types such as `empty`, `punc` and `other`.

### Revised finding

The existence of these nodes is **not itself a bug**. The CUC usability problem is that they are all exposed simply as `word` nodes without a word-level type that distinguishes lexical words from gap/punctuation/editorial objects.

A `word_type` feature analogous in purpose to the DSS word `type` would make downstream word counts and n-grams much safer.

---

# 4. No lexical-text inconsistency was found between `g_cons` and the sign layer

This was the most important corpus-integrity check.

For every one of the **27,242 words with non-empty `g_cons`**, the audit reconstructed its consonantal form from its descendant sign slots.

Before filtering non-consonantal signs:

| Result | Words |
| --- | ---: |
| Exact match | **26,719** |
| Match after removing `.` dividers | **506** |
| Remaining mismatch | **17** |

The remaining 17 are entirely explained by the other known editorial signs (`?` and `…`, sometimes together with `.`). After filtering the four non-consonantal sign values (`.`, `?`, `-`, `…`) as well as whitespace:

> **27,242 / 27,242 non-empty `g_cons` words reconstruct correctly from their sign slots.**

This is strong evidence against corruption or dropped lexical letters in the canonical TF layer.

It also suggests a very useful permanent invariant for the test suite:

> concatenate all descendant signs with `type=cons` → result must equal `g_cons` for every lexical word.

DSS already tests essentially this relationship.

# 5. Every sign slot belongs to exactly one word

The audit counted word membership for every one of the 146,017 slots.

| Number of containing word nodes | Sign slots |
| --- | ---: |
| exactly 1 | **146,017** |
| 0 | **0** |
| more than 1 | **0** |

So the word layer forms a complete, non-overlapping partition of the sign slot stream.

This is structurally clean, but it reinforces why non-lexical word typing matters: gap and punctuation objects are deliberately participating in the same complete word partition as lexical words.

# 6. Whitespace has two distinct roles

Of the **68,256 whitespace slots**:

- **38,541** are marked `emen=restored`;
- **29,629** have no `emen` value;
- the remaining **86** are associated with `excised`, `redundant`, `missing` or `remark`.

The position of the **29,629 un-emended whitespace slots** is especially informative:

| Position within containing word | Count |
| --- | ---: |
| trailing | **29,099** |
| internal | **327** |
| placeholder-only word | **202** |
| leading | **1** |

So two different phenomena are being represented with whitespace:

1. restored/gap width and other editorial spacing;
2. ordinary trailing spacing after words.

The first is a defensible palaeographic/editorial representation. The second behaves much more like a token separator or layout convention.

Again, the main issue is not that either exists. It is that both currently look like the same node type to an API consumer.

# 7. The 0.2.7 → 0.2.8 slot increase is now explained much more precisely

The earlier review noted that sign slots increased from **117,594** in 0.2.7 to **146,017** in 0.2.8, a change of **+28,423**.

The complete comparison shows:

| Slot class | 0.2.7 | 0.2.8 | Change |
| --- | ---: | ---: | ---: |
| visible | 77,244 | 77,761 | **+517** |
| ASCII space | 35,024 | 62,931 | **+27,907** |
| NBSP | 5,326 | 5,325 | **-1** |

The most revealing positional change is:

> **un-emended trailing ASCII-space slots: +28,970**

In 0.2.7 there were only **2** such slots; in 0.2.8 there are **28,972**.

Other whitespace categories were simultaneously redistributed, which is why the net ASCII-space increase is +27,907 rather than +28,970.

This makes the change much less mysterious: **0.2.8 started attaching ordinary trailing ASCII whitespace to word slot spans on a corpus-wide scale.**

The consonantal layer itself is much more stable. In both releases the `cert` feature has exactly:

- 53,664 `True` values;
- 23,551 `False` values;

for a total of **77,215 cert-bearing consonantal signs**.

The +517 visible-slot increase is therefore outside the consonantal/cert-bearing inventory and is numerically identical to the 517 divider-dot slots present in 0.2.8. This is consistent with 0.2.8 also moving/adding word-divider material into the sign stream.

### Verdict

This is **not evidence that 0.2.8 lost or fabricated Ugaritic letters**.

It is, however, a substantial **representation/API compatibility change**. Code that uses:

```python
len(F.otype.s('sign'))
```

or:

```python
len(L.d(word, 'sign'))
```

as a consonant count changes meaning dramatically between releases.

That change should be documented as a schema/model migration and protected by tests.

# 8. Divider information is split between sign slots and `trailer`

CUC documents [`trailer.tf`](../../tf/0.2.8/trailer.tf) as interword material. In 0.2.8:

- **13,900** word nodes have `trailer='.'`;
- **13,870** have no trailer value.

At the same time, the sign stream itself contains **517 `.` slots**, each mapping to Ugaritic `𐎟` in `usign`.

Those dot slots occur both internally and at word boundaries:

- 391 dot slots are the last visible sign of their word;
- 126 are internal visible signs.

There are also words that contain a dot sign **and** have `trailer='.'`:

- 54 words have an internal dot plus a dot trailer;
- 9 words have a trailing dot plus a dot trailer;
- 1 word contains both internal/trailing dots and a dot trailer.

The internal cases can naturally encode more than one divider position. The 10 cases with a boundary dot plus a dot trailer should be checked against the source before deciding whether a repeated divider is intentional. They are **not classified as bugs here**.

What is already clear is that a caller cannot treat either the sign layer or `trailer` alone as the complete abstract notion of “word divider”. The representation is mixed.

---

# 9. `otext.tf` is still an interface problem

CUC defines:

```text
@fmt:text-orig-full={sign}
@fmt:text-orig-unicode={usign}
```

in [`tf/0.2.8/otext.tf`](../../tf/0.2.8/otext.tf).

This omits `trailer`/`utrailer`, even though 13,900 words have explicit trailer dividers. The custom app compensates by manually appending a word's trailer when rendering its last sign.

The comparator corpora use a clearer convention:

- DSS full text formats include punctuation and `{after}`;
- Syriac uses `{g_cons_utf8}{trailer}`;
- ExtraBiblical includes its word-level suffix/spacing material in its full-text formats.

Because CUC also stores some divider material directly as sign slots, the correct fix is **not necessarily** to append trailer blindly to every format. The 10 boundary-dot-plus-trailer cases show why.

The required invariant should instead be:

> The documented standard full-text format reconstructs the intended transcription losslessly and exactly once.

That reconstruction needs a test against the canonical editorial representation.

---

# 10. The `cert` renderer mismatch is a genuine bug

[`tf/0.2.8/cert.tf`](../../tf/0.2.8/cert.tf) contains only:

- `True`;
- `False`;
- absence.

The corpus-wide audit shows an especially clean contract:

- exactly **77,215** consonantal signs carry `cert`;
- all whitespace and the 546 non-consonantal/editorial visible signs are outside that boolean inventory.

But [`app/app.py`](../../app/app.py) still contains:

```python
if F.cert.v(n) != 'uncertain':
    material = f"""<em>{material}</em>"""
```

This condition is true for `True`, `False`, and absence, so it cannot express the current certainty distinction.

The repository history explains how this happened. In TF 0.2.5, the feature still used the literal value `uncertain`. By TF 0.2.6/0.2.7, the same early sign positions use `False` instead. The app renderer was not migrated with the feature vocabulary.

Given the feature name and the historical mapping, `False` appears to represent the old uncertain state. The exact display predicate should still be confirmed against the intended KTU italics convention, but the current predicate is definitely wrong.

---

# 11. Tablet integrity checks are reassuring

The full audit found:

- **0 tablets with no visible signs**;
- **0 tablets with no non-empty `g_cons` words**;
- **0 exact duplicate groups** when hashing the ordered visible-sign sequence of each tablet;
- **0 exact duplicate groups** when hashing the ordered non-empty `g_cons` word sequence of each tablet.

This rules out the suspected pathological cases such as a tablet record consisting only of spacing or two labels pointing to exactly the same textual content.

It does not rule out legitimate or accidental **near duplicates**, quotations, repeated formulae, or different witnesses of the same composition. Those require a different, philologically informed comparison.

---

# 12. What should change

The audit no longer supports deleting whitespace slots or empty words as “bad data”. Doing so could destroy editorial information.

The safer improvements are:

1. **Add an explicit sign-type feature.** Researchers should be able to distinguish consonants, separators, dividers, editorial signs and gap/empty material without inspecting raw characters.
2. **Add an explicit word-type feature.** At minimum distinguish lexical/glyph words from gap/empty, punctuation and other editorial objects.
3. **Make `g_cons` reconstruction a hard integrity test.** Concatenating consonantal descendant signs must reproduce `g_cons` for every lexical word. The current data pass this test for all 27,242 non-empty words.
4. **Document the 0.2.8 slot-model migration.** The +28,970 ordinary trailing-space change makes raw sign counts incompatible with 0.2.7.
5. **Fix the `cert` renderer against the actual boolean vocabulary.** Add a test that verifies the intended uncertain sign is italicized and the certain sign is not.
6. **Define one canonical lossless text reconstruction.** Test sign/divider/trailer interaction, especially the boundary-dot-plus-trailer cases.
7. **Keep non-lexical words, but make them queryable.** Word counts, n-grams and lexical coverage should not silently include 528 gap/punctuation/editorial objects.
8. **Fix the README tablet count** from 278 to 279 or generate it from TF.
9. **Keep provenance work separate but improve it.** Empty `@source`/`@manuscripts` is a reproducibility/documentation gap, not a TF-format violation.

---

# Final assessment

The canonical CUC TF 0.2.8 data are substantially more internally coherent than the initial spot checks suggested.

Most importantly:

- **no lexical text loss was found**;
- **all non-empty `g_cons` words are reconstructible from the sign layer** once known non-consonantal signs are filtered;
- **all empty `g_cons` words are explainable non-lexical objects**;
- **every tablet contains real text**;
- **no exact duplicate tablet content was found**.

The central weakness is therefore not corpus corruption. It is **an under-specified public data model**.

CUC has effectively adopted a DSS-like mixed sign stream, but without DSS's explicit `type` information. As a result, the data preserve useful distinctions internally while exposing node names (`sign`, `word`) that invite a simpler interpretation than the data actually support.

For researchers, the highest-value fix is to make those hidden categories explicit and enforce the reconstruction invariants in the root test suite. The separate `cert` renderer mismatch and README count discrepancy remain straightforward bugs.
